Concept

Best-first search: one algorithm, three behaviors

Uniform-cost search, greedy best-first search, and A* are the same algorithm with different priority functions. All three keep a frontier of discovered but unexpanded nodes in a priority queue. Each round, they pop the lowest-priority node, stop if it's a goal, and otherwise generate its children and push them.

AlgorithmPriority of node nWhat it optimizesOptimal?
Uniform-cost search (UCS)g(n)Cheapest so far. Expands in rings of equal cost, like ripples.Yes, but slow.
Greedy best-firsth(n)Looks closest to the goal. Ignores how far it has already traveled.No.
A*g(n) + h(n)Estimated total cost of the cheapest path through n.Yes, if h is admissible.

g(n) is the actual cost from the start to n. h(n) is a guess of the remaining cost from n to a goal. A* adds them to estimate the full cost of the best path that goes through n, and always expands the node with the lowest estimate.

Admissible and consistent heuristics

  • Admissible: h(n) ≤ h*(n), where h* is the true cheapest remaining cost. The heuristic is never too pessimistic. This guarantees A* never pops a goal by a suboptimal path while a better one is still in the frontier.
  • Consistent: h(n) ≤ cost(n, n') + h(n') for each step. This is a triangle inequality: one step can't reduce the estimate by more than it costs. Consistent heuristics are also admissible. Manhattan distance on a grid with unit costs is consistent.
  • Dominance: If two heuristics are both admissible and h₂(n) ≥ h₁(n) everywhere, then A* with h₂ never expands more nodes than with h₁. Larger is better, as long as it stays admissible.
Why heuristics speed things up With h = 0, A* is UCS. It has no sense of direction and explores evenly in every direction until the cheapest path's cost is reached. A good heuristic adds a "this way" bias. Nodes leading away from the goal get high g + h and stay in the queue. The closer h is to h*, the more nodes are skipped. With h = h*, A* only expands nodes on an optimal path.

Details of this implementation

  • The returned num_steps counts calls to problem.step, meaning children generated, not nodes popped. This is the number 1A prints and the natural metric for 1B.
  • Ties are broken by the state (the heap stores (priority, state, node)), so runs are deterministic. The notebook relies on this for grading.
  • The goal test happens when a node is popped, not when it's generated. This is what makes A* optimal: a goal may be generated through an expensive path before the cheap path is found.
  • A child is added if it's new, or if it was reached before by a more expensive path.

1B · A better heuristic

Code + written answer · reference heuristic: 12 lines

run_astar_search_faster(problem, step_budget=10000) → (states, actions, costs, num_steps)

How to design one: relax the problem

The standard way to get an admissible heuristic is to solve an easier version of the problem exactly. Remove a constraint, and the optimal cost of the easier problem can't be higher than the real one. Removing constraints never makes the trip longer.

Here, remove the walls and one-way doors. The robot must still (1) reach the patient and (2) take them to the hospital. Without walls, each leg is the Manhattan distance:

If not carrying the patient: h = |robot − patient|₁ + |patient − hospital|₁
If carrying the patient: h = |robot − hospital|₁

|a − b|₁ means |a.row − b.row| + |a.col − b.col|. Every step costs exactly 1, and the walls only remove options. So the true cost is at least this value, and the heuristic is admissible.

Why both legs? "Manhattan distance to the hospital" alone is admissible but weak: it ignores the detour to the patient, and in this maze the patient is in the opposite direction from the hospital. "Manhattan to the patient only" ignores the return trip. The two-leg version is the largest of these and still admissible, so by dominance it expands the fewest nodes. You can compare these choices in the widget in 1A.

Implementation shape

You can't easily override SimpleProblem.h because the problem is a frozen dataclass. You don't need to: write a heuristic function inside run_astar_search_faster that reads problem.patient_loc and problem.hospital_loc, and use it in the priority lambda.

What "outperforms" should mean in your answer

The notebook leaves this open. A good answer measures two things:

  1. Work: compare num_steps (calls to problem.step) for the old and new heuristics. You could also time both, but step counts are deterministic and easier to compare.
  2. Quality: show that the total path cost is unchanged. A faster search that returns a worse path isn't better. This is what admissibility guarantees, and you should show it, not just claim it.

The widget in 1A runs the same algorithm, so its numbers should match yours. If your num_steps disagrees, check the tie-breaking and the carrying case.

Hint 1: don't forget the carrying case. After pickup, the robot is standing where the patient was, but problem.patient_loc still holds the patient's original location. If you always use the two-leg formula, you'll count a leg the robot has already traveled, and the heuristic can overestimate after pickup. Check state.carried_patient.
Hint 2: code skeleton. 
def run_astar_search_faster(problem, step_budget=10000):
    def manhattan(a, b):
        return abs(a[0] - b[0]) + abs(a[1] - b[1])

    def h(state):
        if state.carried_patient:
            return manhattan(state.robot_loc, problem.hospital_loc)
        return (manhattan(state.robot_loc, problem.patient_loc)
                + manhattan(problem.patient_loc, problem.hospital_loc))

    return run_best_first_search(
        problem, lambda n: n.g + h(n.state), step_budget)

Concept

How the fire spreads, and how to predict it

The rule

At every time step, each cell independently chooses one cell from its 3×3 neighborhood, including itself, with probability proportional to the weight matrix W. It then copies that neighbor's fire value from the previous step. Neighbors outside the grid count as "no fire."

With the default W = [[0,1,0],[1,4,1],[0,1,0]], a cell keeps its own value with probability 4/8 and copies each of its four direct neighbors with probability 1/8. In just_wait, the center weight is 20, so a cell keeps its value 20/24 ≈ 83% of the time and fire moves slowly. In the_circle, only the center weight is nonzero, so nothing ever changes.

Why this matters for planning Fire doesn't just grow, it also drifts and dies out. Fire spreads by copying, and the edge of the grid always supplies "no fire," so the expected amount of fire slowly decreases over time. A cell that's dangerous now may be safe in 30 steps. That's the reason waiting can be a good plan.

From samples to probabilities: the marginal update

For planning, we don't want one random future. We want the probability that each cell is on fire at time t, given the fire we see now. This is the marginal probability of each cell. It's easy to compute because of linearity of expectation.

Start with the notebook's suggested example: two cells X and Y, uniform weights. At each step, X copies itself or Y with probability ½ each. So:

P(Xt = 1) = ½·P(Xt−1 = 1) + ½·P(Yt−1 = 1)

This works because "which neighbor X copies" is chosen independently of the current fire. The rule holds for the probabilities just as it does for the 0/1 values. In general:

Pt(i, j) = Σneighbors (i′, j′) W̃[i′ − i + 1, j′ − j + 1] · Pt−1(i′, j′)   =   (Pt−1 ⊛ W̃)(i, j)

Here W̃ is W normalized to sum to 1. This is exactly what FireProcess.dist computes. It was written for a 0/1 grid, but it works the same on a grid of probabilities. So:

P0 = the observed fire grid (0s and 1s)
Pt = dist(Pt−1)   — apply the same convolution t times
I checked this against simulation: averaging 20,000 sampled 5-step fire runs matches the repeated-convolution marginals to within about 0.005 in every cell. The formula is exact for single-cell marginals. The approximation only appears later, when we treat different cells and times as independent.

Concept

Determinization: turning "survive the fire" into a shortest-path problem

The fire MDP is hard to plan in directly. Its state includes the whole fire grid, which has 2(rows×cols) possible values. The idea behind Part 2 is to drop the fire from the state and account for it through the step costs instead.

Step 1: what are we optimizing?

Pick a fixed sequence of moves. Its chance of success is the probability of not burning at any step. If we treat each step's fire as independent (an approximation, discussed below), this is a product:

P(survive the plan) ≈ ∏t (1 − pt),   where pt = P(fire at the robot's cell at time t)

Step 2: turn the product into a sum

Shortest-path algorithms add costs along a path. Taking a log turns a product into a sum, and negating turns "maximize" into "minimize":

maximize ∏(1 − pt)  ⇔  maximize Σ log(1 − pt)  ⇔  minimize Σ −log(1 − pt)

So the step cost is −log(1 − p). It's 0 when the cell is certainly safe (p = 0), small for small p (about p), and infinite when the cell is certainly on fire (p = 1). The cheapest path is the plan most likely to succeed.

The extra c = 1e-6 per step does two things. It breaks ties toward shorter plans, and it gives every step a positive cost, so A* doesn't treat endless loops through safe cells as free.

Try it: costs add up to survival probability

A three-step plan. Set the fire probability at each step. The sum of the step costs is exactly −log(probability of surviving all three steps).

Step 3: put time in the state

Fire probabilities change over time, so the cost of stepping into cell (3,1) depends on when you get there. The determinized state is therefore (robot_loc, carried_patient, time), and time indexes into the precomputed marginals Pt.

Why time is the key to "just wait" There's no "stay" action. But with time in the state, ((0,1), False, t=3) and ((0,1), False, t=5) are different states. A* can find plans that walk back and forth along the safe top row while the fire near the corridor dies down, then go. Without time in the state, revisiting a cell would look like a pointless loop and "waiting" couldn't be expressed.

Step 4: replan every step

The agent doesn't follow the whole plan. It takes only the first action, sees the real new fire grid, and replans from scratch using that observation. This is receding-horizon replanning. It corrects a lot of the approximation error, because the plan is always based on what's actually burning now.

What determinization gets wrong

  1. Independence across time. If a cell isn't on fire now, it probably won't be next step either. The product formula ignores this, so it's pessimistic about long paths near fire. In just_wait, for the route straight down and back up without waiting, the determinized survival estimate is about 0.39. Simulating that exact route gives about 0.50.
  2. Open-loop evaluation. Each plan is scored as if the robot will follow it no matter what happens. Replanning means it won't, but the choice between plans doesn't account for that. Routes that keep options open are undervalued. This is the topic of 2D.

Why the heuristic is scaled by c

Each step costs c + (−log(1 − p)), and the fire term is ≥ 0. So any path to the goal of length L costs at least c·L, and L is at least the Manhattan distance. Therefore c × Manhattan is admissible. Without the scaling, Manhattan would be on the order of 10 while real costs are on the order of 10⁻⁶ to 1, so it would overestimate badly and A* would no longer find the safest plan.

This heuristic is weak: the fire term usually dominates the cost and the heuristic ignores it entirely. That's acceptable, because it's still admissible and the search is still correct. It's just closer to uniform-cost search than to an informed A*.

Which time index to use

The formula in the notebook charges for on_firet+1(st+1): the danger is where you end up, at the time you arrive. This matches the real reward. FireMDP.step moves the robot and samples the next fire grid together, and you burn if the new grid has fire at your new location. Since s2.time = s1.time + 1, use fire_dist_at_time(s2.time)[s2.robot_loc].

Common mistakes
  • Using p at the old cell or the old time. This is an off-by-one error that makes the agent react one step late.
  • log(0). If p = 1 exactly, −log(1 − p) is inf and NumPy prints a warning. That's correct (never step there), but clip p to something like 1 − 1e-12 or return float("inf") explicitly to avoid the warning.
  • Integer arrays. The observed fire grid is boolean. Convert it with .astype(float) before convolving, or the probabilities may be cast back to 0/1.
  • Recomputing from scratch. Computing dist t times for each of thousands of A* expansions is very slow. Compute Pt from the cached Pt−1.
  • Deep recursion. A recursive fire_dist_at_time(t-1) works but can hit Python's recursion limit at large t. A loop that fills the cache up to t is safer.
  • "Log-likelihood" vs. probability. The notebook text says fire_dist_at_time computes the log-likelihood, but the function's docstring says it returns the marginal distribution. Either works as long as step_cost matches. Returning probabilities is simpler.

def fire_dist_at_time(self, t):
    cache = self.fire_dists_cache
    if 0 not in cache:
        cache[0] = self.fire_process.initial_fire_grid.astype(float)
    k = max(cache)                    # largest t computed so far
    while k < t:
        cache[k + 1] = self.fire_process.dist(cache[k])
        k += 1
    return cache[t]

You only write determinized_problem · reference: 36 lines including the provided code

determinized_problem(self, state: FireMDPState) → DeterminizedFireMDP

act is already written. It builds a determinized problem starting from the current real state, runs A*, and returns the first action. Your job is to build that problem: a copy of the original, but with

  • the robot starting where it is now,
  • the fire starting from the fire grid observed now, so that P0 is today's real fire, and
  • the patient already carried if the robot has picked them up.

The dataclasses.replace(obj, field=new_value) function returns a copy of a frozen dataclass with some fields changed. Use it on self.problem.pickup_problem and self.problem.fire_process, then build a new DeterminizedFireMDP from them.

The common bug: losing the patient after pickup PickupProblem has no field for "starts carrying the patient." Its initial property computes it as initial_robot_loc == patient_loc. After pickup, the robot moves away from the patient's original cell, so if you only update initial_robot_loc, the new problem thinks the patient is still waiting at their old location. The agent then goes back for someone it's already carrying, and in a one-way maze it may not be able to.

Fix: if state.carried_patient is true, also set patient_loc=state.robot_loc. Then initial returns carried_patient=True, step keeps it true (carried or ...), and the heuristic's "carrying" case applies.
Why build a new problem every step? The marginals Pt depend on the fire you observe now. If the fire next to the corridor happens to die out, the new P0 shows that, and every future Pt becomes safer. A new DeterminizedFireMDP also gets an empty fire_dists_cache (it's a default_factory), so marginals from an old observation are never reused.

def determinized_problem(self, state):
    pp = self.problem.pickup_problem
    patient = state.robot_loc if state.carried_patient else pp.patient_loc

Why the determinized agent tends to choose down

Think about how each option is evaluated. The determinized planner scores a fixed sequence of cells. For the room, it must pick one specific route through the room now, using today's marginals, and that route has to cross cells that are moderately likely to be on fire. It can't express "I'll go around whichever fire is in the way when I get there." A smart agent in the room would see where the fire is and route around it. The value of that flexibility is called option value, and open-loop scoring ignores it.

The corridor gives no flexibility either way, so open-loop scoring rates it accurately. Comparing an accurately scored corridor with a room scored too pessimistically biases the choice toward the corridor.

Toy model: open-loop vs. closed-loop scoring

This is a simplified version of the choice, not the real map. The corridor has k cells with fire probability q each. To get through the room, you must cross one gap, and there are m gaps, each blocked by fire independently with probability p. The open-loop planner commits to one gap now. A closed-loop agent looks first and takes any open gap.

Concept

Monte Carlo tree search

MCTS skips both the probability calculations and the determinization. It uses the MDP only as a simulator: problem.step(state, action) draws a real random next state, including a sampled fire grid. The planner repeatedly imagines futures from the current state, records which first actions led to good outcomes, and spends more simulations on the promising ones.

One iteration, four phases (as in run_mcts_search)

  1. Select. Starting at the root, pick an action at each tree node using UCB (below), then sample a next state from the simulator. Continue until you reach a node with no children yet, or a sampled next state the tree hasn't seen.
  2. Expand. Add a child for every action at that leaf, pick one at random, and sample its next state.
  3. Simulate. From there, play random actions until the episode ends or the horizon is reached, adding up discounted reward. This is done n_simulations = 10 times and averaged.
  4. Back up. Pass the value up the path, updating each action's total value U and visit count N. With max_backup=True, a state's value is the best average among its actions, not the average of everything tried.

After iteration_budget iterations, it returns the root action with the highest average value U/N.

UCB: balancing exploration and exploitation

UCB(a) = U(a)/N(a)  +  C·√( ln N(parent) / N(a) )

The first term favors actions that have worked well (exploit). The second term is large for actions tried only a few times (explore), and it shrinks as an action is tried more. Untried actions get UCB = ∞, so every action is tried at least once. C controls the balance; the default is √2.

This is the same idea as PS7's exploration bonus k / (N + 1), applied to planning instead of learning.

Try it: which action does UCB select next?

U is the sum of values backed up through that action. Rewards are between −1 and +1. N(parent) is taken as the sum of the N values.

Why MCTS should handle 2D's problem better

  • Real samples, not marginals. Rollouts use FireProcess.sample, so fire stays correlated over time. No independence approximation.
  • Closed-loop values. Inside the tree, the robot's next action is chosen after the sampled fire is known. In principle, a branch where the robot enters the room and adjusts to the fire is scored by how well it can adjust.
Honest caveats
  • The tree is shallow here. A state includes the whole fire grid, and every step samples a new grid. The same next state almost never appears twice, so select creates a new leaf after about one level. With 10–50 iterations, the tree is roughly "one level of real choices, then random rollouts." (In the_circle, the fire never changes, so states repeat and the tree can grow deeper.)
  • Random rollouts are a weak value estimate. They estimate "how well does a random walk do from here." Random walks rarely reach the hospital within 40 steps on the larger maps. So the values mostly measure "how likely am I to burn soon," and push only weakly toward the goal.
  • Because of both of these, results are noisy with small budgets. Larger iteration_budget values help, and the notebook encourages trying them if you have time.
The baseline, RolloutLookaheadAgent: for each action, it runs 10 random rollouts and picks the action with the best average. This is like MCTS with no tree and no UCB, only the "simulate" phase. With receding_horizon=0, the rollouts have length 0, every action scores 0, and the agent acts at random.

Why the horizon property matters

There are two situations:

  • Finite-horizon problems (maze, horizon 20): at time t, only horizon − t steps remain, so the planner shouldn't look further than that. planning_horizon computes this from self.t, which is why you must keep self.t updated.
  • Infinite-horizon problems (the others): you can't search forever, so you look ahead a fixed amount (receding_horizon, 40 in the benchmarks) every step. The lookahead window moves forward with you.
Common mistakes
  • Forgetting state=state. The default is problem.initial, so the agent would plan from the starting position every step.
  • Incrementing self.t before reading planning_horizon, which makes the horizon one step too short.
  • Not passing C and iteration_budget. The function defaults (iteration_budget=100) would silently override the agent's settings and invalidate your 10-vs-50 comparison.

How to read the reward numbers

Each run ends near +1 (rescued, slightly discounted, e.g. 0.99920 ≈ 0.98), near −1 (burned), or exactly 0 (timed out in maze). So the mean reward is roughly (success rate) − (burn rate). A mean of 0.6 means roughly 80% success and 20% burns, or a mix that includes timeouts. Because the results are essentially success/failure, the standard deviation is large almost by necessity. Report a success rate next to the mean; it makes the table much easier to read.

What to look for

Don't assume these patterns; check your table for them. Here's what the analysis above predicts:

  • the_circle: the fire never moves, so the problem is effectively deterministic and the marginals are exact. Determinization has no disadvantage here. Does the determinized agent do as well as or better than everything else?
  • maze: no fire, but a 20-step horizon. The danger is timing out, not burning. Random rollouts see no reward signal in a fire-free maze (every rollout scores 0 unless it happens to reach the goal), so look at whether the rollout and MCTS agents have many 0 rewards here.
